# Two-Stage Reranking Engine (`ranking_agent`)

The AI Factory Two-Stage Reranking Engine enhances Knowledge Oracle queries, autonomous debates, and evidence validation by pairing fast, high-recall vector search (Stage 1) with precise cross-encoder semantic reranking (Stage 2).

---

## 1. Architecture: Bi-Encoder vs. Cross-Encoder

Standard single-stage RAG retrieves text by comparing dense embedding vectors generated by a **Bi-Encoder** (e.g. `bge-m3`, `text-embedding-004`). While Bi-Encoders are fast and scalable via approximate nearest neighbor (ANN) indexes, they project entire passages into static vector embeddings, losing subtle token interactions, exact keyword relevance, and query-context nuances.

The AI Factory implements a **Two-Stage Retrieval Pipeline**:

```
┌─────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                  TWO-STAGE RETRIEVAL PIPELINE                                   │
│                                                                                                 │
│  [User / Architect Query]                                                                       │
│                            │                                                                    │
│                            ▼                                                                    │
│  [STAGE 1: Dense Vector Retrieval + Multi-Table RRF Fusion]                                    │
│  • Embeds query using embed_model (bge-m3, qwen3-embedding)                                      │
│  • Performs parallel vector KNN search across all LanceDB tables                                │
│  • Merges candidate lists using Reciprocal Rank Fusion (RRF, Cormack et al. SIGIR 2009):        │
│        RRF_Score(d) = Σ_{t ∈ Tables} [ 1 / (60 + rank_t(d)) ]                                  │
│  • Retrieves deep candidate pool: recall_k = 30 (or k * 4)                                      │
│                            │                                                                    │
│                            ▼                                                                    │
│  [STAGE 2: Cross-Encoder Semantic Reranking (_rerank_chunks)]                                   │
│  • Passes full (Query, Document) pairs simultaneously through a deep Transformer               │
│  • Full cross-attention across all query and document tokens                                    │
│  • Computes calibrated relevance_score for each passage                                         │
│  • Sorts descending by relevance_score and slices top_k = 5 chunks                              │
│                            │                                                                    │
│                            ▼                                                                    │
│  [Prompt Injection / Grounding Context]                                                         │
│  • Synthesizes grounded answer or validates claims using the top 5 highest-relevance chunks     │
└─────────────────────────────────────────────────────────────────────────────────────────────────┘
```

### Key Invariants
1. **Recall Depth (`recall_k`)**: Stage 1 casts a wide net (default `recall_k = 30` or `max(k * 4, 30)`), ensuring relevant chunks that scored moderately in cosine distance are surfaced for deep inspection.
2. **Context Precision (`top_k`)**: Stage 2 filters the candidate pool down to the highest-scoring `top_k = 5` chunks, eliminating vector noise and protecting the LLM's context window.
3. **Fail-Open Fallback**: If the remote reranker endpoint is offline or times out, the engine outputs a warning to `stderr` and gracefully falls back to the Stage 1 vector/RRF order without halting the pipeline.

## 2. Supported Execution Backends

The reranker supports both **Remote HTTP Endpoints** (zero client VRAM usage) and **In-Process Local Execution** (via `sentence-transformers`).

### 2.1 Remote HTTP Endpoint (Recommended for Local Clusters)
When `ranking_api_base` (or `ORACLE_RANKING_API_BASE`) is configured, `_rerank_chunks` sends JSON payloads directly to an OpenAI-compatible or Text Embeddings Inference (TEI)-compatible reranker endpoint.

* **Dual-Key Payload Compatibility**:
  To ensure interoperability across both TEI endpoints (which expect `texts`) and Jina / Cohere endpoints (which expect `documents`), payloads are serialized with dual keys:
  ```json
  {
    "model": "jinaai/jina-reranker-v3.5",
    "query": "What is the formula for leverage ratio?",
    "documents": [
      "Passage 1 text...",
      "Passage 2 text..."
    ],
    "texts": [
      "Passage 1 text...",
      "Passage 2 text..."
    ],
    "top_n": 5
  }
  ```
* **Endpoint URL Auto-Resolution**: Automatically normalizes base URLs, targeting `{base}/v1/rerank` and falling back to `{base}/rerank` if a 404 status code is encountered.
* **Score Extraction**: Parses `relevance_score` or `score` from returned candidate dictionaries and assigns `candidate["_relevance_score"] = float(score)`.

### 2.2 In-Process Local Execution (`sentence-transformers`)
When `ranking_api_base` is unset or empty, the engine executes the model locally in-process:

```python
from sentence_transformers import CrossEncoder

# 1. Offline-First Cache Loading (Zero Network Lag, Zero Unauthenticated HF Warnings)
try:
    _RERANKER_LOCAL_INSTANCE = CrossEncoder(model, trust_remote_code=True, local_files_only=True)
except Exception:
    _RERANKER_LOCAL_INSTANCE = CrossEncoder(model, trust_remote_code=True, local_files_only=False)
```

#### Local Execution Invariants & Tokenizer Recovery
1. **Offline-First Cache Invariant**: `local_files_only=True` is attempted first. This guarantees zero outbound network requests and silences unauthenticated Hugging Face Hub telemetry warnings on air-gapped systems.
2. **Tokenizer Pad Token & EOS Binding**: Modern LLM-based rerankers (Qwen / Jina) often lack an explicit `pad_token`. The engine automatically binds `pad_token = eos_token` and synchronizes `model.config.pad_token_id` to prevent `batch_size > 1` tokenizer crashes.
3. **Chat Template Recovery**: LLM rerankers that use Jinja chat formatting require specific `query` and `document` role mapping. If missing or misconfigured, the engine injects:
   ```jinja
   <Query>: {{ messages | selectattr("role", "eq", "query") | map(attribute="content") | first }}
   <Document>: {{ messages | selectattr("role", "eq", "document") | map(attribute="content") | first }}
   ```
4. **2D Logit Score Calibration (`_extract_score`)**:
   Cross-encoders with binary classification heads output 2D logit vectors `[negative_logit, positive_logit]`. The score extractor safely retrieves the positive relevance class (`val[-1]`) rather than taking `val[0]`:
   ```python
   def _extract_score(val):
       if hasattr(val, "__len__") and not isinstance(val, (str, bytes)):
           return float(val[-1]) if len(val) > 1 else float(val[0])
       return float(val)
   ```
5. **In-Memory Cache Singleton**: The model instance is cached in module memory (`_RERANKER_LOCAL_INSTANCE`) across turns, eliminating repeated initialization latency.

## 3. Configuration Reference (`.env.yml`)

Configure the reranker globally under `endpoints` and per-phase under `models` and `rag`:

```yaml
endpoints:
  ranking_api_base: "http://192.168.100.1:8080/v1" # Remote reranking endpoint

phases:
  - name: "Implementation Phase"
    models:
      ranking_agent: "jinaai/jina-reranker-v3.5"    # Model identifier / HuggingFace repo
      rag_agent: "gemini/gemini-2.5-flash"
      embed_model: "gemini/text-embedding-004"

    rag:
      collection_name: "working_repo_lib"
      retrieval_mode: top_k
      recall_k: 30                                 # Stage 1 candidate pool depth (default: 30)
      top_k: 5                                     # Stage 2 final context chunks (default: 5)
```

## 4. Integration Across Subsystems

### 4.1 Knowledge Oracle (`oracle_agent.py`)
During `/run aider-oracle "<query>"` or autonomous debates:
1. `_retrieve(query, k)` queries LanceDB with `recall_k = max(k * 4, 30)` or `ORACLE_RECALL_K`.
2. Fuses multi-table results via RRF.
3. Invokes `_rerank_chunks(query, rows, top_n=k)`.
4. Stderr logs the attribution and chunk count: `[oracle] 5 source chunk(s) from 2 file(s) ...`.

### 4.2 Evidence Validator (`validator.py`)
In `_region(block, db_dir, collection, k)`:
1. Embeds the review passage and fetches `recall_k` candidates across tables.
2. Runs RRF fusion.
3. Passes the passage and candidate chunks through `_rerank_chunks(block, rows, top_n=k)`.
4. Uses the highest `_relevance_score` directly as the semantic region similarity score (`sim = float(rows[0]["_relevance_score"])`).

## 5. CLI Flags & Overrides

Both `aider-oracle` and `aider-validate` expose CLI flags for ad-hoc inspection and debugging:

```bash
# 1. Override recall depth on ad-hoc Oracle queries
aider-oracle --recall-k 50 "What is the exact formula for leverage ratio?"

# 2. Temporarily bypass Stage 2 reranking (use vector KNN order directly)
aider-oracle --no-rerank "What is the exact formula for leverage ratio?"

# 3. Claims-only validation with reranking
aider-validate --claims-only --file summary.md --recall-k 40

# 4. Claims-only validation bypassing reranker
aider-validate --claims-only --file summary.md --no-rerank
```

### Environment Variables
| Variable | Default | Purpose |
| :--- | :--- | :--- |
| `ORACLE_RANKING_MODEL` | `""` | Active reranker model name (e.g. `jinaai/jina-reranker-v3.5`). |
| `ORACLE_RANKING_API_BASE` | `""` | Base URL for remote reranker server. |
| `ORACLE_RECALL_K` | `30` | Number of Stage 1 candidate chunks fetched before reranking. |
| `ORACLE_NO_RERANK` | `0` | Set to `"1"` to bypass Stage 2 reranking globally. |

## 6. How to Deploy a Dedicated Reranker Server

### Method A: Text Embeddings Inference (TEI) via Podman/Docker
Text Embeddings Inference (TEI) by HuggingFace is the fastest cross-encoder server:

```bash
podman run --gpus all -p 8080:80 \
  -v /home/user/.cache/huggingface:/data \
  ghcr.io/huggingface/text-embeddings-inference:latest \
  --model-id jinaai/jina-reranker-v3.5 \
  --port 80
```

### Method B: LiteLLM Proxy Routing
If managing multiple models through a central LiteLLM proxy (`config.yaml`):

```yaml
model_list:
  - model_name: jinaai/jina-reranker-v3.5
    litellm_params:
      model: jina_ai/jina-reranker-v3.5
      api_key: os.environ/JINA_API_KEY
```

Set `endpoints.ranking_api_base: "http://<litellm-proxy>:4000/v1"` in your `.env.yml`.

## 7. Academic Foundations & Literature References

1. **Reciprocal Rank Fusion (RRF)**:
   - **Paper:** Cormack, G. V., Clarke, C. L., & Buettcher, S. (2009). *Reciprocal rank fusion outperforms Condorcet and individual rank learning methods.* Proceedings of the 32nd International ACM SIGIR Conference on Research and Development in Information Retrieval (SIGIR '09), 758–759.
   - **DOI:** [10.1145/1571941.1572114](https://doi.org/10.1145/1571941.1572114)
   - **Theoretical Contribution:** Establishes that combining rank positions via $\sum \frac{1}{k + r(d)}$ with smoothing constant $k=60$ consistently outperforms individual IR rankers and Condorcet voting without score normalization vulnerabilities.

2. **Cross-Encoder Neural Reranking**:
   - **Paper:** Nogueira, R., & Cho, K. (2019). *Passage Re-ranking with BERT.* arXiv preprint [arXiv:1901.04085](https://arxiv.org/abs/1901.04085).
   - **Theoretical Contribution:** Demonstrates that full cross-attention across concatenated (Query, Document) tokens eliminates the embedding bottleneck of dual-encoders, yielding significant MRR@10 and NDCG improvements.
